# Integración futura en ASE

La decisión de producto es **API sin frontend propio**. ASE contendrá las pantallas, navegación, visualización de diferencias y experiencia de usuario. Este repositorio proporciona el servicio HTTP versionado y la CLI. Fuera de ASE se utilizará Git para obtener el código, Docker/Python para levantarlo y Swagger para probarlo.

1. **Consumo:** el backend/gateway de ASE configura la URL privada del servicio y llama a `/api/v1`. `/openapi.json` es el contrato para generar o implementar el cliente. No se abre una segunda aplicación visual ni se comparte una base de datos con ASE. Los endpoints devuelven resultados y hallazgos estructurados para su presentación en ASE.
2. **Identidad:** ASE mantiene el login del usuario. La API deberá validar una identidad verificable, por ejemplo un access token OIDC delegado o credenciales de servicio autenticadas junto con contexto de usuario firmado. Se validan issuer, audiencia, firma, caducidad y scopes. No se implementa un segundo formulario de login ni se confía en cabeceras arbitrarias de usuario/organización. Configuración y claves se suministran por entorno/gestor de secretos.
3. **Acceso al producto:** un adaptador de entitlements verifica sujeto/organización contra un contrato versionado o claims firmados de corta duración. Deben definirse caché, revocación y fallos cerrados. La suscripción no sustituye los permisos sobre proyectos.
4. **Organizaciones:** se añade UUID interno de organización y mapeo único de `(issuer, external_org_id)`. La membresía y la organización activa se verifican en servidor. El navegador no podrá elegir un tenant sin autorización.
5. **Cambios backend pendientes:** migraciones de organización/membresía, claves de ámbito en entidades, repositorios de contratos/comparaciones con ámbito obligatorio, RBAC, aislamiento de exports y eventos de auditoría. Reemplazar el adaptador local de proyectos y las consultas directas por interfaces con contexto autenticado. Añadir pruebas cruzadas de tenant en cada lectura/escritura y considerar RLS en PostgreSQL como defensa adicional.
6. **Pruebas independientes:** Docker levanta solo esta API con SQLite y documentación Swagger en loopback. La CLI sigue comparando ficheros sin base ni identidad. Un modo integrado deberá rechazar configuración incompleta de autenticación/autorización. No se añaden URLs, credenciales ni dependencias ASE hardcodeadas.

Actualmente están implementados el contrato HTTP, la persistencia y el comparador. **La conexión real con ASE, la autenticación y el aislamiento multiusuario están pendientes.** Antes de uso público faltan pruebas de permisos, revocación, CSRF/origin según transporte, cuotas, aislamiento de workers, observabilidad y recuperación operativa.
